# Legendary Online 实施计划

## 1. 项目目标

从当前仓库重新建立一个可真实运行的多人 2D ARPG 学习项目，用于补齐 Java 游戏服务端岗位需要的实时通信、场景管理、战斗同步、数据持久化和性能测试能力。

最终主线：

```text
Unity 2D 客户端
        |
        | TCP + Protocol Buffers
        v
Java 21 游戏服务端
        |
        +-- Netty 网络层
        +-- Session 会话管理
        +-- Scene 场景循环
        +-- 玩家、怪物、战斗
        +-- 状态同步和广播
        |
        +-- MySQL
        +-- Redis
        +-- Kafka

Spring Boot 管理接口作为外围服务，后置实现。
```

项目定位：具备企业级 Java 后端经验，并通过真实联机项目补齐游戏服务端能力的 Java 游戏服务端工程师。

## 1.1 招聘市场对齐原则

项目优先选择招聘 JD 中高频且能够通过作品集证明的能力：Java 并发与网络编程、Netty/TCP、游戏服务端权威逻辑、MySQL/Redis、消息队列、Linux/Docker、测试、性能分析和故障定位。每项能力必须有对应的实现、测试或可复现运行证据，不以技术名词堆砌作为完成标准。

## 2. 当前基线

- 当前仓库已建立第一阶段 Maven 多模块工程、协议 Schema、Netty 启动骨架和 Java Bot 占位入口。
- 新主线从多人服务端工程重新建立，不继承历史工程的目录、模型或构建约束。
- 每个阶段都必须在可运行的前提下推进，不提前声称尚未完成的功能。

## 5. 质量门槛

单元测试覆盖移动速度、边界、攻击距离、冷却、伤害、奖励和 Session 状态迁移。

集成测试覆盖 Netty 连接、Protobuf 编解码、登录、心跳、进入场景、移动广播、攻击广播、断线清理、重连恢复、持久化和事件发送。

端到端测试至少验证两个客户端登录、同场景可见、移动同步、战斗同步、怪物死亡、奖励到账、断线重连和服务端重启后的角色恢复。

每个阶段完成后必须执行聚焦测试、`git diff --check` 和文档更新，再进入下一阶段。

## 6. 不提前承诺的内容

- 不在压测前写入在线人数、延迟或吞吐量数字。
- 不把 MySQL、Redis、Kafka、Flink 写成已经完成的能力。
- 不伪造个人在其他项目中的职责、数据或性能贡献。
