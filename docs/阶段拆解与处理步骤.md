# 阶段拆解与处理步骤

## 1. 文档目的

本文把 Legendary Online 的实现过程拆成大单元和单元内部步骤，方便按企业项目方式推进、验收和复盘。

原则：范围可以阶段化，质量不能降低。每个大单元都必须同时说明目标、输入、处理步骤、输出、验收方式和当前边界。

## 2. 总体处理链路

```text
客户端或 Bot
    -> TCP 连接
    -> Netty ChannelPipeline
    -> LengthFieldBasedFrameDecoder
    -> GameMessageDecoder
    -> GameMessageDispatcher
    -> SessionRegistry
    -> Scene CommandQueue
    -> Scene Tick
    -> 状态广播
    -> 客户端表现
```

当前已经完成到 `SessionRegistry` 的最小登录和心跳闭环，`Scene CommandQueue` 之后的场景、移动和战斗仍待实现。

## 3. 大单元一：基础工程

### 目标

建立可维护的 Java 21 Maven 多模块工程，为服务端、协议、Bot 和后续客户端联调提供稳定结构。

### 内部步骤

1. 建立根 `pom.xml`，统一 Java 21、依赖版本和插件版本。
2. 建立 `game-protocol`、`game-server`、`game-bot` 模块。
3. 在 `game-server` 下按职责拆分 `game-network`、`game-world`、`game-battle`、`game-player` 和 `game-server-bootstrap`。
4. 建立 `docs/`、`plan/` 和项目协作规则。
5. 执行 `mvn clean test` 或聚焦模块测试，保证基础构建可重复。

### 验收

- Maven 能使用 Java 21 编译。
- 根工程或聚焦模块测试通过。
- 文档中明确当前已实现和未实现范围。

## 4. 大单元二：协议层

### 目标

建立 Java 服务端、Java Bot 和后续 Unity 客户端共享的二进制协议。

### 内部步骤

1. 在 `.proto` 中定义业务消息体，例如登录、心跳、进入场景、移动和快照。
2. 通过 `protobuf-maven-plugin` 生成 Java 类。
3. 定义 14 字节自定义消息头：`magic`、`protocolVersion`、`flags`、`messageType`、`requestId`、`bodyLength`。
4. 使用 `LengthFieldBasedFrameDecoder` 解决 TCP 半包和粘包。
5. 使用 `GameMessageDecoder` 把完整帧解析成 `GameMessage`。
6. 使用 `GameMessageEncoder` 把 `GameMessage` 写回字节流。

### 验收

- `ProtocolCodecTest` 覆盖 Protobuf 往返编解码。
- `FrameDecoderTest` 覆盖半包场景。
- 非法 magic 会被协议层拒绝。

## 5. 大单元三：网络连接与 Session

### 目标

建立客户端连接、登录身份和服务端在线 Session 的绑定关系。

### 内部步骤

1. `GameServer` 使用 `NioServerSocketChannel` 监听端口。
2. 每个客户端连接创建一个 `SocketChannel` 和独立 `ChannelPipeline`。
3. `GameMessageDispatcher` 接收解码后的 `GameMessage`。
4. 收到 `LoginRequest` 后，`SessionRegistry` 创建 `ClientSession` 并绑定到当前 `Channel`。
5. 收到 `HeartbeatRequest` 后，服务端检查当前连接已登录，再返回 `HeartbeatResponse`。
6. `channelInactive` 时清理 `SessionRegistry` 中的在线索引。

### 当前边界

- 当前只实现最小登录和心跳闭环。
- 暂未实现重复登录、顶号、心跳超时、重连恢复和未登录错误响应。
- 当前账号与玩家 ID 是临时生成，不代表真实账号系统。

### 验收

- `GameMessageDispatcherTest` 验证登录响应、Session 注册、心跳响应和断线清理。
- `game-bot` 能通过真实 TCP 链路完成登录和心跳。

## 6. 大单元四：Bot 联调

### 目标

用 Java Bot 作为真实客户端，验证服务端进程的 TCP、协议、登录和心跳链路。

### 内部步骤

1. 启动 `game-server-bootstrap`。
2. Bot 连接 `127.0.0.1:9000`。
3. Bot 发送 `LoginRequest`。
4. 服务端返回 `LoginResponse`。
5. Bot 校验 `ErrorCode.OK`、`sessionId` 和 `playerId`。
6. Bot 发送 `HeartbeatRequest`。
7. 服务端返回 `HeartbeatResponse`。
8. Bot 主动关闭连接，服务端触发 Session 清理。

### 验收

- Bot 日志出现登录成功和心跳响应。
- 服务端没有异常堆栈。
- 聚焦测试命令通过。

## 7. 大单元五：场景与移动

### 目标

把网络请求转换成场景命令，由场景 Tick 线程顺序处理玩家状态。

### 内部步骤

1. 定义 `SceneCommand` 和命令队列。
2. 登录玩家进入默认场景。
3. `MoveRequest` 只表达方向和输入序号，不提交最终坐标。
4. 场景 Tick 校验方向、速度、边界和输入序号。
5. 场景生成 `PlayerPositionSnapshot` 或 `SceneSnapshot`。
6. 网络层向相关客户端广播状态。

### 当前边界

- 尚未实现移动、广播和地图碰撞。
- 后续必须保证场景状态不被多个 Netty Worker 线程直接修改。

## 8. 大单元六：战斗与奖励

### 目标

实现服务端权威战斗闭环，客户端只提交攻击意图，服务端负责命中、伤害、死亡和奖励。

### 内部步骤

1. 补齐攻击、伤害、实体移除协议。
2. 定义怪物、玩家属性和技能配置。
3. Tick 中校验攻击冷却、距离和目标状态。
4. 服务端计算伤害并更新生命值。
5. 怪物死亡后生成奖励事件。
6. 广播伤害、死亡和奖励结果。

### 当前边界

- 尚未实现战斗协议和战斗模块。
- 不提前写性能数字和完整 MMORPG 能力。

## 9. 大单元七：持久化与工程化

### 目标

在主链路稳定后接入企业级后端能力，包括 MySQL、Redis、Kafka、Docker、监控和压测。

### 内部步骤

1. 使用 MySQL 保存账号、角色、背包、装备和任务。
2. 使用 Redis 保存在线状态、排行榜和短期缓存。
3. 使用 Kafka 发布登录、移动、战斗、死亡和掉落事件。
4. 使用 Bot 批量压测连接、登录、移动和战斗。
5. 记录 P50、P95、P99、Tick 耗时和队列堆积。
6. 通过 Docker Compose、日志、监控和 JFR 形成可复现实验。

### 当前边界

- MySQL、Redis、Kafka 和 Flink 尚未实现。
- 任何性能指标必须来自实测结果。
