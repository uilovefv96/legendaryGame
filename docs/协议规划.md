# Legendary Online 协议规划

## 1. 传输分层

```text
TCP connection
    -> LengthFieldBasedFrameDecoder
    -> custom message header
    -> Protocol Buffers payload
    -> message dispatcher
    -> Scene CommandQueue
```

Protobuf 只负责消息体的结构化编码和解码；TCP 可靠传输、Netty 连接管理、拆包粘包、心跳和消息路由由网络层负责。

## 2. 消息头

第一版建议使用固定长度或明确长度字段的消息头：

| 字段 | 用途 |
|---|---|
| `protocolVersion` | 协议大版本协商 |
| `messageType` | 路由到对应 Protobuf 消息 |
| `requestId` | 请求和响应关联 |
| `errorCode` | 响应错误表示 |
| `bodyLength` | TCP 帧边界 |

第一版冻结为 14 字节大端序消息头：

```text
magic          2 bytes
protocolVersion 1 byte
flags          1 byte
messageType    2 bytes
requestId      4 bytes
bodyLength     4 bytes
```

其中 `magic` 用于快速拒绝非本协议数据，`messageType` 用于选择 Protobuf 消息类型，`requestId` 用于请求与响应关联，`bodyLength` 表示 Protobuf 消息体长度。业务错误码放在响应消息体中，不放入传输层消息头。

具体字节布局在实现阶段冻结，并在本文件补充。

## 3. 第一版消息目录

- `LoginRequest` / `LoginResponse`
- `HeartbeatRequest` / `HeartbeatResponse`
- `EnterSceneRequest` / `EnterSceneResponse`
- `MoveRequest`
- `PlayerPositionSnapshot`
- `SceneSnapshot`
- `AttackRequest`
- `DamageEvent`
- `EntityRemovedEvent`
- `DisconnectEvent`

## 4. 兼容性规则

- 字段编号一旦发布，不得复用。
- 删除字段必须使用 `reserved` 保留编号和名称。
- 新字段追加编号，旧客户端忽略未知字段。
- 不随意修改已有字段类型。
- 枚举保留 `*_UNSPECIFIED = 0`。
- 破坏性变更提升 `protocolVersion`，并保留迁移窗口。
- 每次协议变更同时更新 `.proto`、生成代码、测试和本文档。

## 5. 安全边界

客户端不提交最终坐标、伤害值、命中结果、经验、金币或怪物死亡状态。服务端只接受方向、技能、输入序号等操作意图，并在场景 Tick 中完成校验和结算。
