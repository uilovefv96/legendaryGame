# Legendary Online 项目规划

## 1. 项目定位

Legendary Online 是一个面向学习和求职展示的多人 2D ARPG 垂直切片项目，通过可运行的联机闭环展示 Java 游戏服务端核心工程能力。

目标岗位方向：Java 游戏服务端工程师，同时保留 Java 后端、搜索和数据平台方向的可迁移能力。

### 就业市场对齐

本项目的第一目标是建立符合招聘市场要求的 Java 游戏服务端作品集，而不是只完成一个能运行的 Demo。参考 Boss 直聘、拉勾网、前程无忧及企业招聘页公开的 Java 游戏服务端和游戏服务器岗位 JD，反复出现的要求主要包括：

| 市场要求 | 项目对应实践 | 交付证据 |
|---|---|---|
| Java 基础、并发和多线程 | 场景 Tick、命令队列、线程边界、Session 生命周期 | 单元测试、线程模型说明、运行日志 |
| TCP/IP、Socket、Netty | 自定义消息头、长度字段分帧、Pipeline、心跳、断线清理 | 网络模块测试、Bot 联调记录 |
| 游戏逻辑和服务端权威 | 移动校验、攻击距离、冷却、伤害、死亡和奖励 | 规则测试、双客户端演示 |
| MySQL、Redis 等存储 | 角色数据持久化、在线状态和短期缓存 | 数据模型、集成测试和运行说明 |
| Kafka 等消息队列 | 发布登录、战斗和运营事件，不参与实时判定 | 事件链路代码和边界说明 |
| Linux、Docker、Maven、Git | 可重复构建、启动脚本、容器化预留和工程规范 | Maven 构建、运行文档、构建记录 |
| 测试、性能和故障定位 | 协议回归、集成测试、Bot、Tick 耗时和队列指标 | 测试报告、压测记录、JFR 或监控数据 |
| 系统设计和技术表达 | 模块边界、协议演进、权威边界和故障处理文档 | `docs/`、`plan/` 和代码注释 |

这些要求用于确定项目优先级，不代表所有能力在当前阶段已经实现。只有完成并验证后，才在 README、简历材料或项目总结中声明对应能力。

本节调研时间为 2026 年 9 月 24 日，岗位信息会随招聘周期变化，后续阶段开始前应重新抽样核对。参考样本包括：[Boss 直聘网易游戏 Java 游戏服务器开发](https://www.zhipin.com/zhaopin/98d0e26961448a8e1XR72t24EA~~/)、[三七互娱 Java 服务端主程](https://zhaopin.37.com/index.php?a=viewPublishDetail&c=index&id=1655&m=mobile)、[吉游网络高级 Java 游戏后端开发](https://learnku.com/java/t/71799) 和 [阿里巴巴游戏服务器开发工程师](https://jobs.ultraai.site/jobs/alibaba_campus/campus%3A199907700013)。

核心闭环：

```text
客户端输入
    -> TCP/Netty
    -> Session
    -> Scene CommandQueue
    -> 20 Tick/s 场景逻辑
    -> 服务端权威校验和结算
    -> 状态广播
    -> 客户端表现
```

## 2. 技术决策

| 领域 | 第一阶段选择 | 决策说明 |
|---|---|---|
| 服务端 | Java 21 | 与现有 Java 能力和岗位方向一致 |
| 实时网络 | Netty + TCP | 学习长连接、Pipeline、EventLoop、心跳和连接生命周期 |
| 消息协议 | Protocol Buffers | Java、Unity C#、Java Bot 共享 Schema，字段类型和演进规则清晰 |
| 客户端 | Unity 2D + C# | 更贴近常见游戏客户端工作流，作为最终客户端路线 |
| 服务端结构 | 模块化单体 | 先降低部署和调试成本，不提前拆微服务 |
| 管理接口 | Spring Boot | 承载登录、查询和 GM 等外围 HTTP 能力，不执行每次实时移动 |
| 持久化 | MySQL | 保存账号、角色、背包和任务等长期数据 |
| 缓存 | Redis | 在线状态、排行榜和短期缓存 |
| 事件流 | Kafka | 发布业务事件，不参与实时 Tick 的同步判定 |
| 实时分析 | Flink，后置 | 主链路稳定后再接入统计和状态计算 |

## 3. 协议选型说明

第一版实时主协议采用 `Protocol Buffers`，原因是：

- 消息体积比 JSON 更紧凑，适合移动、心跳和战斗事件。
- Java 服务端、Unity C# 客户端和 Java Bot 可以从同一份 `.proto` 生成代码。
- 字段类型、枚举和字段编号明确，联调错误更容易在构建或解码阶段暴露。
- 新增和废弃字段有成熟的兼容规则，适合客户端和服务端分阶段发布。
- 与 Netty 的长度字段分帧和 Pipeline 组合清晰。

`FlatBuffers` 暂不作为第一版默认协议。它适合大型场景快照、低分配和直接访问 buffer 的场景，但第一版消息主要是小型命令和事件，先引入会增加 Builder、生命周期和调试复杂度。等 Profiling 证明场景快照或客户端 GC 是瓶颈后，再评估将大型只读快照单独改用 FlatBuffers。

`MessagePack` 可用于 Bot、内部工具或非核心数据交换。它接入灵活，但如果用在长期维护的跨语言主协议上，需要额外建立字段顺序、版本兼容和 Schema 约束，不如 Protobuf 直接。

协议分层：

```text
实时游戏消息：TCP + Netty + Protocol Buffers
管理后台接口：HTTP + JSON + Spring Boot
调试和测试工具：JSON 或 MessagePack
大型快照优化：基于 Profiling 决定是否引入 FlatBuffers
```

## 4. 模块职责

### `game-protocol`

维护 `.proto` Schema、错误码、消息类型和代码生成配置，不包含游戏规则。

### `game-server`

模块化单体服务端，建议按以下边界拆分：

- `game-server-bootstrap`：进程启动、配置、优雅停机。
- `game-network`：Netty、编解码、连接和心跳。
- `game-world`：场景、实体、Tick、命令队列和广播。
- `game-battle`：移动校验、攻击、伤害、死亡和奖励。
- `game-player`：Session、玩家状态和角色生命周期。
- `game-persistence`：MySQL、Redis 和事件发布适配。

### `game-client`

Unity 2D 表现层，负责输入采集、动画、插值、UI 和服务端状态展示，不负责最终坐标、伤害、奖励或死亡判定。

### `game-bot`

Java 模拟客户端和压测工具，复用 `game-protocol`，用于连接、协议回归、断线恢复和性能测试。

### `game-admin`

Spring Boot 管理后台，后置实现。管理命令通过安全命令入口交给游戏线程，不直接修改场景对象。

第一阶段不创建空的 `game-persistence`、`game-admin` 和 Unity 工程；这些模块在有真实职责和可验证场景后再加入。

## 5. 第一版游戏范围

只实现一个场景和一类怪物，包含登录、进入场景、两个客户端同时在线、玩家移动和位置广播、普通攻击、攻击冷却和距离校验、怪物受伤和死亡、经验和金币奖励、离场、断线清理和重连后的场景恢复。

暂不包含多服分区、跨服、复杂职业装备任务系统、真实商业化账号体系、生产级高可用和未经实测的性能承诺。

## 6. 服务端权威边界

客户端发送操作意图：

```text
MoveRequest { direction, inputSequence }
AttackRequest { skillId, direction, inputSequence }
```

服务端决定最终坐标、是否允许移动和攻击、攻击是否命中、伤害、死亡、经验、金币以及场景广播内容。
